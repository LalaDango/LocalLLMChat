# 既知の問題・ワークアラウンド（LocalLLMChat向け縮約版）

最終更新: 2026-07-07

> 「SMで対策済み」の問題は、SM（PC上の別ミドルウェア）経由でのみ保護されるという意味。
> **LocalLLMChat等のFLM直結クライアントでは未対策のまま**なので、アプリ側で対策する場合の参考にする。

## キャッシュ／checkpoint関連（FLM本体の性質・全経路共通）

### 容量超過prefill強行によるcheckpoint全滅（2026-07-05実証）

- **症状**: 容量超過のprefill強行 → FLMのprefillが途中停止 → checkpoint 0リセット →
  以後は全量prefillも容量超のため復旧手段なし＝セッション構造的死亡
- 天井の発現モードは2種: ①生成中にふわっと到達（200＋空content＋kv不変）
  ②prefill前から構造的超過（FLM 400 or 接続断）
- **直結クライアントは無防備**。送信前にKV実測値＋入力見積りでガードするのが正道

### キャッシュミスの発生条件（v0.9.43確定）

- checkpoint照合は「最終user発言を除く履歴全体の完全一致」（トークン単位diff・最新checkpointのみ）
- ミスを誘発するもの:
  - **U+3000（全角スペース）** → 半角正規化で解決（対策前miss 5/6 → 対策後0/6）
  - assistant履歴と生成実物の1トークンのズレ → 次の1リクエストのみ全量prefill
  - 複数メッセージの一括追加 → 復元行われず無言で全量prefill
- ミス検出式（2026-07-06更新・前ターンとの差分方式）:
  `余剰 = prompt_tokens + completion_tokens + 前ターンactive_kv_tokens − 今回active_kv_tokens`
  が前ターンKV相当ならミス（全量prefill）、≈0ならヒット（"Use cached prompt!"ログは信頼不可）。
  単純な大小比較（`active_kv ≫ prompt+completion` ならヒット）は履歴が小さいと誤判定する（実機実証）

### シングルキャッシュスロット（従来からの制約・現在も有効）

- Serve再起動・モデル切替・別セッション切替でキャッシュ破壊
- 運用中のmodel名変更は厳禁（キャッシュ全滅・約46秒ロード）
  ※ LocalLLMChatの翻訳機能が別モデルを呼ぶ場合はこれに該当する点に注意

## e4bの挙動特性の問題

### 位置参照のとり違え（2026-07-04実証）

- **症状**: 高占有帯（72%〜で実証）で「直近3件」「N回前の」等の位置指定を毎回とり違える
- **真因**: 忘却ではなく位置アドレスの崩壊（内容名指しなら正解＝記憶は保持）
- **対策**: 過去ターン参照は必ず内容・タイトルで名指しさせる

### gemma4系の role:"tool" 無視問題（2026-07-07解決・クライアント側変換で対処）

- **症状**: OpenAI形式のツールループで、e4bがStep1のツール呼び出し自体は成功するのに、
  role:"tool"で返した実行結果を**無視して直前の質問を再掲**する
- **真因（濃厚）**: FLMのgemma4テンプレート実装がrole:"tool"を落としている疑い。
  HF公式のgemma-4 chat_template.jinjaにはネイティブの`<|tool_response>`畳み込みロジックが
  **存在する**のに無視される＝モデルではなくFLM側の実装問題。ガイダンスプロンプト強化や
  ツールdescription改善では直らない（実機検証済み）
- **解決策（LocalLLMChat v2実装・実機＋ハーネス30リクエスト検証済み。commit c1250af）**:
  送信時のみ、gemma4系モデル判定時に以下の変換を行う（DB/表示は無変更）:
  - role:"tool" → role:"user"、content = 各行 `[ツール {name}({args}) の実行結果] {result}` を
    改行連結 + 末尾に「この結果を踏まえて応答してください」1回（連続tool結果は1メッセージにマージ）
  - **argsは必ず含める**: e4bは本文なし・tool_callのみを返すことがあり、その場合
    質問内容はargsの中にしか存在しない
  - assistant（tool_call発行側）: 本文があれば本文のみ送信、**空ならメッセージ自体をスキップ**
    （tool_callsフィールドは送らない）
  - 変換は決定的（DB行+モデル名の純関数）であること。揺れると毎ターンキャッシュミス
- **教訓（フォーマット模倣）**: v1では assistant側に `[ツール呼び出し: name(args)]` の
  畳み込みテキストを置いたところ、**モデルが「自分の発言書式」として学習し、本物のtool_callの
  代わりに平文で書式を模倣**する副作用が発生。assistant履歴にツール呼び出し風の書式を
  置いてはいけない。呼び出し情報はuser側（結果メッセージ）に「実行結果の報告」形で統合する
- **user連続はシロ（確定）**: assistant本文なしスキップにより `user→user` の連続が発生するが、
  FLMは30/30リクエストで正常処理。Gemmaテンプレートの交互制約懸念は実測で否定された

### e4bのツール発火は「ムラ」ではなく「閾値」（2026-07-07ハーネス実測）

- プロンプトに**ツール名を明示すれば言語不問で100%発火**、なければほぼ0%という二極挙動:
  - 「ツールでクイズ出して」（名前なし）: 0/5
  - 「必ず ask_user_question ツールを使って出題すること」（JA名指し）: 5/5
  - 英語名指し: 5/5 ／ 「今何時？」（get_datetime、descriptionと強一致）: 5/5
- **対策**: コード修正不要。プロンプト/プリセットにツール名を焼き込むだけで制御可能
- 結果追従（変換後）: datetime 5/5、クイズ実質4/5＋GRAY1（正誤判定を飛ばして即次問を
  tool_callする挙動が約1/5で発生。多段ループ上は合法だがUX上は判定スキップ）

### ツール使用会話は毎ターン全量prefill（構造的宿命・許容）

- checkpointにはモデル生出力（`<|tool_call>`構文込み）が刻まれるが、クライアントの再構築履歴は
  変換後テキスト → トークン列が一致せず**ツールを使った会話は以降毎ターン全量prefill**。
  `<think>`除去と同じ構図。小規模会話では実害なし、30K級ツール会話でのみ約60秒税
- 検証資産: `scripts/flm_tool_harness.py`（当リポジトリ）— アプリのペイロードを忠実再現し
  FLM直叩きで発火率・追従率を自動測定。FLM更新やプロンプト書式変更時の回帰チェック用

## まとめ生成の品質問題（LocalLLMChatの要約機能に直接関連）

（2026-03発見・9B/4B共通傾向。e4bでの再検証は未実施）

- 「次のステップ」「手順？」トピック混入／特定項目の欠落／訂正→再まとめのイタチごっこ
- **対策**: まとめは1回だけ出させる（漏れは訂正メモの追加のみ）。正確な記録が要る場合は
  入力時に結論・カテゴリを明示させ、外部（Claude側等）で校正する
